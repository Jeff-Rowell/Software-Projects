Introduction 
1.1. Purpose 
 
For the purposes of this project, this document specifies and explains the architecture and behavior of requirements inferred by the implementation of "customization and internationalization" within the Master Teacher software application.  
 
Scope 
The scope of intended features can be broken down into three high-level categories.  
Internationalization – The ability to easily localize content for a target audience using resource files for language translations. 
Customization – Directly related to localizing content, this feature allows for custom labeling of tabs within the curriculum view.  
Time Zones – Ability to display local time based on browser settings or profile settings on a per-user basis.  
 
1.2.1 Internationalization and Localization 
Internationalization specifically refers to implementing the ability to localize, or translate, the application's user interface for a specific region, culture, or locale. In the case of this project, internationalization infers the ability to use specific resource files to support multiple language translations of the user interface. Such language specific resource files contain localized strings of translated content for the user interface. Provided there is more than one language specific resource file, the user will be able to change the default language within their profile settings. Changing this setting will cause the respective language resources to be loaded in place of the default language resource files. The scope of implementation will encompass the entire user work-flow: from initial login, to changing localization settings and having them stored and retrieved at the user’s next use. 
1.2.2 Customization 
Customization within this project refers to the ability for user groups to customize different tab headers in CW master teacher. The current scope is to implement the ability customize the labels of tabs in the curriculum view. This customization will be done at the institution(group) level. Each user within a group will see the same tab headers which can be customized by the group admin. Implementing this feature will involve adding the customized tabs to the Institution DBObject. Updating the appropriate factories and controllers will also be required along with managing default values for groups that are not using the custom tab feature. A new view to allow for modifying the tabs will also be required. 
1.2.3 Time Zones 
Time zones are also an important consideration when localizing content of a software application. Hence, a requirement within the scope of this project is to support displaying the local time to users based on their detected browser settings. Implementation of the time zone component into CW Master Teacher will impact the database structure by adding additional parameters to models in the database. All related models, views, controllers, repositories, and factories will also be impacted. Updates to the user interface will be required to allow a user to easily adjust their time zone. Currently, CW Master Teacher displays all times in Mountain Standard Time (MST), and stores all times in the database in UTC. The product possesses a pair of functions which exist to convert times to and from local/UTC, but assumes local times are always in MST. (These functions are named ConvertLocalTimeToUtc and ConvertUtcToLocalTime, and are located in CWMasterTeacherDataModel/Utilities.cs. Such functions must be updated to accommodate displaying local time as determined by the browser settings or user's preferred local time settings).

1.5. Overview of Document 
In the remainder of this document you will find an overview of the system architecture, including an overview on each of the affected components in the product; as well as detailed descriptions on each of these components. The architecture section contains an overview on the structure and relationships of each component as well as class diagrams for both the components and the user interface. Section three contains a more in depth description on each of the components and how they will be individually impacted by the integration of the required features into the product. These features have been categorized into three specific subsets including the ability to assign a time zone, customization of tabs within the curriculum view, and general support for the future localization of text fields, descriptions, and annotations across many languages. 
 
2. Architecture 
 
2.1. Overview of modules / components 
 
2.1.1 Internationalization and Localization 
This structure will follow the build of Diagram A. In essence it begins with the IStringLocalizer which has a CultureInfo class. Inside of CultureInfo we have access to name, number format, textInfo, ThreeLetterISOLanguageName as well as a TextInfo class which contains the Boolean value isRighttoLeft using all of these we can appropriately access and display strings from multiple languages.  
The chain to follow will begin with the localizer which will be accessed when a string needs to be drawn to the screen. The culture info will be fed to the interface along with the string ID used in the selected component. The localizer will then go through culture info to see if specific formats need to be used via the TextInfo class and number format variables. Using these we can not only get the correct string but also the proper way to display it. 
 
2.1.2 Customization

This will be an entry added to the Institution DBobject. It will contain a list of key value pairs for custom tab strings.

This will be a new option added to the admin drop down menu allowing the admin of a group to customize tab labels. 
2.1.2.3: Optional Parameter in IStringLocalizer for Using Custom Labels 
IStringLocalizer can take an optional parameter. When this parameter is passed the database will be searched for a custom string corresponding to the label.

This component gives users the ability to create a “Class Selection”. When creating a class selection, days and times are selected for a given course. 
2.1.3.2. Class Meeting Component

2.1.3.3. Document Component 
When documents are uploaded to the curriculum for a lesson plan, this component displays the document along with the day and time it was uploaded. 
2.1.3.4. Message Board Component 
The Message Board allows users to leave messages for themselves and others who use a curriculum. When messages are posted on the message board, the message, along with the date and time it was posted, are displayed on the message board.

This component requires the addition of a link to the user interface so that users have the option to manually configure their time zone. 
2.1.3.6. Utilities Component 
Update the Utilities class so that times are being dynamically converted to and from the current local time (to be displayed to the user) and to and from UTC (to be stored in database).

2.3. User interface issues 
While the overall layout and design of the user interface is intended to remain unchanged, there are some design issues that must be considered while adding support for customization of time zones, tab labels, and basic language translation. 
 
Updates to all affected views within the user interface must be made to ensure local times and languages are properly displaying. Throughout this process it is important to verify that all relevant strings are properly localized to support the swapping of language specific resource files without negatively impacting the user interface. 
 
Much like specifying a user-specific language or time zone, customizing the labels of tabs will occur on a customization (or translation) settings page whereby the user can provide their own custom labels for each tab located in the curriculum view. 
 
Scaling management for text must be implemented within the UI, at its most basic level this should simply be a hover over to See the full text if it's too large to fit in said UI component. At its final level the UI should be able to rescale itself to compensate for different text sizes and changing UI components. 
 
Additionally, the ability to show text from left to right and right the left is an important consideration for various languages with different orientations.  
 
Finally, Time zone specification will be additionally configurable from the graphical user interface within the functioning web page, running on the user’s browser. This option for additional configuration by the user requires updating the User DbObject within CWMasterTeacherDataModel and updates to all related Controllers, Factories, Repositories, and other DbObjects that implement the User DbObject. 3.2 Customization 
3.2.1. Institution DBobject – New Hashset Field for Custom Labels 
A new entry to the Institution DBobject will be required for this implementation. The entry will be a hashmap of key value pairs of the original string and the custom string the institution is using for that label. The Institution object can be accessed through the User DBobject. Each user has an associated Institution and the current user can be accessed in CurriculumView which is where the custom labels will be loaded.  
3.2.2. View for Editing Custom Labels 
New view for editing the tab names. This page should be added to the admin drop down menu so it can only be accessed by group admins. A simple implementation for this view could be similar in appearance to the create/edit user form currently in the application. Each listing should be a current tab label with a text entry box next to it. At the bottom of the page the user can confirm/update changes which will write to the new labels to the DB. When making this page it is critical that the key value pairs written to the database correspond to the references in the CurriculumModelFactor listed under section 3.5. If these values do not correspond then the custom values will not be displayed even if they exist in the database. 
3.2.3. Custom Logic in IStringLocalizer for Using Custom Labels 
IStringLocalizer is being used for implementing internationalization. Resources with the ability to be customized will be called the same way as they normally would however an optional parameter will be passed in which will indicate the label could be customized. If this parameter is present then the normal IStringLocalizer procedure will be interrupted and the CustomLabel field of the Institution DBobject corresponding to the current user will be searched. If a custom string is found for the corresponding resource then the custom string will be displayed. If no custom string is found then the normal logic for the IStringLocalizer will be followed and the default for the currently language will be displayed. 
3.2.4. Views/Curriculum/Index.cshtml changing hard coded tab names to references 
There are 2 labels in the above file under the Nav Tabs section that are hard coded. These labels will need to be changed to references similar to the other 3 labels using the @model tag 
3.2.5. CurriculumModelFactory, CurriculumViewModel 
This curriculum view model file will need to be updated to enable customization. After the hard coded strings from 3.1.2.5 have been changed to references there will be 5 references to the labels we wish to customize in this file. The current names of these references are: NarrativeTypeName, LessonPlanTypeName, DocumentsTabText, and the 2 references added in 3.1.2.5. 
3.2.6. CurriculumModelFactory 
After the Curriculum model has been updated the corresponding factory method must also be altered. The 2 references added in section 3.1.2.5 need to be added to the BuildCurriculumViewModel method. All 5 of the custom tab references will be updated to use IStringLocalizer through the internationalization process. In order to enable customization for these tabs an optional parameter will also need to be passed to IStringLocalizer to indicate there may be custom stings in the Institution DBObject. This parameter will lead to the custom logic in 3.1.2.4.  
 
 
3.3 Time Zones 
3.3.1. Class Selection Component 
When users create class sections they are selecting days and times relevant to a given course. When a new class selection is submitted, it persists in the database as a ClassSelection DbObject. ClassSelections contain a collection of ClassMeetings which persist the selected class selection days and times as member variables. When time zones are integrated into the product, the Class Selection component will be impacted by displaying times relevant to a user’s current time zone. 
3.3.2. Class Meeting Component 
The class meeting component contains DateTime objects named StartTime and EndTime respectively. These times are stored in the database in UTC format and need to be displayed to the user in their local time zone. Displaying times to the user in their local time zone will be integrated by using the time conversion functions included in the Utilities class. The Utility functions will be leveraged in the mutator functions for StarTimeLocal and EndTimeLocal (in ClassMeeting). See details on the utilities component for more information on how this conversion will be performed. 
3.3.3. Document Component 
By making the time a document was uploaded visible to each user, times must be converted to a user’s local time zone using the Utilities time conversion functions. These Utility functions will be integrated into the get function included in the Document class for DisplayName. DisplayName returns a string containing the user who uploaded the document, along with the date the document was modified (stored in a member variable, DateModified). The Utility time conversion functions will convert the DateModified item to the user’s local time. 
3.3.4. Message Board Component 
The Message Board contains a collection of messages posted by different users. The Message class contains a TimeStamp member variable that is persisted to the database. This TimeStamp will be converted to the user’s local time by using the Utilities time conversion functions in the mutator functions for TimeStamp. 
3.3.5. Configure Time Zone UI Component 
This component requires the addition of two parameters to the User mode. These parameters include a bool member variable called localTimeZoneIsSet which will be set to true as soon as the user specifies a default time zone (in the setLocalTimeZone function). The second member variable is localTimeZone and is of type TimeZoneInfo. When a user selects a default time zone, that time zone is persisted in the database by way of this variable. In order to gain access to these variables, additional functions must be added. The functions are as follows: hasLocalTimeZoneSet(), which returns the value of the member variable, localTimeZoneIsSet. In order to get a user’s default time zone, the accessor method, getLocalTimeZone() will return the current time zone default for that user. When a user takes action to set a new time zone through the GUI, that time zone will be set on the User model through the setLocalTimeZone function. 
By adding additional fields to the User model, all dependent classes must also be updated. This includes updating the member variables and functions in UserRepo, UserModelFactor, UserViewModel, and UserController classes to leverage the additional parameters for local time zone. See the class diagram in section 2.3 User Interface Issues for a detailed outline on the affected classes, variables, and functions. 
3.3.6. Utilities Component 
The Utilities time conversion functions include: ConvertLocalTimeToUtc and ConvertUtcToLocalTime. Currently these functions exist with “Mountain Standard Time” hard coded as the default value for time zone. If a default time zone has not been configured by the user, time zone can be retrieved by the http request header using ASP.NET’s HttpRequest.Headers property (see https://msdn.microsoft.com/en-us/library/system.web.httprequest.headers(v=vs.110).aspx for more information).  Based on the time zone component of the http request header, an appropriate conversion can be made to display/store information to the database by integrating that TimeZoneInfo into the time conversion functions within the Utilities class. This will require the addition of a TimeZoneInfo parameter being passed to the time conversion functions in the Utilities class to circumvent the current behavior of a hard coded time zone. 
 
 
4. Design Decision and Tradeoffs  
 
First login will use cultureInfo pertaining to the user’s current location. This seems like it will set the cultureInfo appropriately for most users at the onset. There will be instances when this will not match the user’s preferences. To accommodate for this, the user will be informed how they may change this to their preference. 
 
After login, the cultureInfo for the user should be saved to the user’s data. This way the cultureInfo will remain consistent throughout the user’s use of the application. Initial cultureInfo for the user can be saved at the initialization of the user.  
 
In order to integrate Internationalization and Localization, we propose a two-step plan for UI concerns.  
 
Initially, the UI should be static and agnostic to the length of label-strings and various other localized elements. If a label does not fit the area with a localization, the text should be abbreviated and fully visible with hovering over the text with the mouse. This first stage ensures that the UI does not get manipulated in an unforeseen way. 
 
The second stage will then focus on updating the UI in such a way that all localized elements show all of their information while also not breaking any UI. One area of initial concern is potential wrapping of items. For example, if all localized labels are very long, then certain elements may be pushed to the second line. An extensive investigation of the UI elements should be done to ensure that the understandability of the UI is not affected adversely if this were to occur.
